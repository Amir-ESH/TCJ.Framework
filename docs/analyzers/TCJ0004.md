# TCJ0004: Domain-event handler lifetime marker is ignored

| Property | Value |
| --- | --- |
| ID | `TCJ0004` |
| Category | `TCJ.DependencyInjection` |
| Default severity | `Warning` |
| Code fix | Mandatory for directly declared TCJ lifetime markers |
| Introduced in | Unshipped |

## Cause

An effectively public concrete type participates in TCJ domain-event handling through `IDomainEventHandler<TEvent>` and also implements one or more of TCJ's six dependency lifetime markers.

When convention scanning is used, TCJ registers domain-event handlers through the dedicated handler-registration pipeline. That pipeline registers discovered handlers as transient services. The marked-dependency registration pass then skips handler types completely, so `ITransientDependency`, `IScopedDependency`, `ISingletonDependency`, `ISelfTransientDependency`, `ISelfScopedDependency`, and `ISelfSingletonDependency` do not control a handler's lifetime.

A lifetime marker on a handler is therefore misleading even when it appears to describe a valid dependency lifetime.

## Rule description

TCJ0004 resolves `IDomainEventHandler<TEvent>` and the six TCJ lifetime markers by metadata identity. It reports an effectively public, non-abstract, non-compiler-generated concrete class when:

- the class implements at least one closed `IDomainEventHandler<TEvent>` contract, directly or through inheritance; and
- the class implements at least one TCJ lifetime marker, directly or through inheritance.

A handler that implements multiple event-handler interfaces produces one diagnostic on the handler type. If several TCJ lifetime markers are present, the diagnostic lists them in the same deterministic marker order used by the convention-registration rules.

Unrelated marker interfaces are ignored.

## How to fix

Remove TCJ dependency lifetime markers from the domain-event handler. The handler pipeline owns convention-scanned handler registration, so dependency markers should not be used to communicate its lifetime.

The automatic **Remove TCJ lifetime markers** fix is offered when every diagnosed TCJ lifetime marker is declared directly on the reported type declaration. It removes only those TCJ marker interfaces and preserves:

- every `IDomainEventHandler<TEvent>` interface;
- other service interfaces;
- unrelated marker interfaces;
- base classes; and
- the handler implementation itself.

When the TCJ marker is inherited through a base class or custom interface, TCJ0004 remains valid but no local automatic fix is offered. The declaration that introduces the TCJ lifetime marker must be reviewed and changed explicitly.

## Examples

### Code with diagnostic

```csharp
using TCJ.Core.DomainEvents;
using TCJ.DependencyInjection.Lifetimes;

public sealed class OrderPlacedHandler
    : IDomainEventHandler<OrderPlaced>, IScopedDependency
{
    public Task HandleAsync(
        OrderPlaced domainEvent,
        CancellationToken cancellationToken)
        => Task.CompletedTask;
}
```

`IScopedDependency` does not make this convention-scanned handler scoped. The domain-event handler pipeline registers it as transient and the marked-dependency pass skips it.

### Corrected code

```csharp
using TCJ.Core.DomainEvents;

public sealed class OrderPlacedHandler
    : IDomainEventHandler<OrderPlaced>
{
    public Task HandleAsync(
        OrderPlaced domainEvent,
        CancellationToken cancellationToken)
        => Task.CompletedTask;
}
```

For the reflection-free path, register the handler explicitly with normal `IServiceCollection` APIs and choose the desired lifetime there instead of adding a TCJ lifetime marker.

## Suppression

Suppress TCJ0004 only when the lifetime marker is intentionally retained for an external convention that is independent of TCJ and the team accepts that TCJ will not honor that marker for domain-event handler registration.

Prefer a narrowly scoped `.editorconfig`, local pragma, or `SuppressMessage`. Removing the misleading TCJ marker is normally clearer than suppression.

## Known limitations

TCJ0004 mirrors the convention scanner's source-relevant boundaries and therefore reports effectively public, concrete, non-compiler-generated handler types. It does not determine whether the containing assembly is actually supplied to a convention-scanning overload at runtime.

The code fix is intentionally conservative for inherited or indirect marker contracts and for partial declarations where the diagnosed marker is not directly removable from the reported declaration. In those cases, the diagnostic is still reported but remediation is manual.

## Compatibility notes

TCJ0004 is a default `Warning` because TCJ can prove that its handler registration path ignores the dependency lifetime marker, but the application may still function and may intentionally register handlers explicitly on the reflection-free path.

This rule does not change runtime registration. Convention-scanned handlers remain registered by the existing handler pipeline with its existing transient lifetime, and the marked-dependency pass continues to skip handler types.
