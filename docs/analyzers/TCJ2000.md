# TCJ2000: Offset paging requires deterministic primary ordering

| Property | Value |
| --- | --- |
| ID | `TCJ2000` |
| Category | `TCJ.Specifications` |
| Default severity | `Warning` |
| Code fix | Unavailable |
| Introduced in | Unshipped |

## Cause

A type derived from `Specification<TEntity>` applies offset paging with `ApplyPaging(skip, take)` on a construction path where TCJ can prove that no primary `ApplyOrderBy` or `ApplyOrderByDescending` configuration exists.

Offset paging without deterministic ordering can produce unstable pages when rows are inserted, removed, or returned in a different provider/query-plan order. `ApplyThenBy` and `ApplyThenByDescending` are secondary ordering operations and do not establish a primary order by themselves.

## Rule description

TCJ2000 analyzes `Specification<TEntity>` construction code and matches the actual TCJ specification method symbols rather than method names alone. A same-named helper or unrelated method does not satisfy the ordering requirement.

The analyzer reports on the `ApplyPaging` invocation only when it can conservatively prove that the relevant constructor or directly associated linear initialization-helper path has no primary `ApplyOrderBy` or `ApplyOrderByDescending` call. Primary ordering can appear before or after `ApplyPaging` during specification construction because the completed specification state, not the call order itself, determines query ordering.

Simple direct initialization helpers are followed when they are source-defined, instance, non-virtual, and have linear bodies that TCJ can reason about safely.

## How to fix

Choose the domain-appropriate deterministic ordering key and configure it with `ApplyOrderBy` or `ApplyOrderByDescending`. Add `ApplyThenBy` or `ApplyThenByDescending` when an additional tie-breaker is required for deterministic results.

No automatic code fix is offered. Selecting an ordering key and direction is domain/query semantics that TCJ cannot infer safely, and guessing a key could silently change consumer-visible paging behavior.

## Examples

### Code with diagnostic

```csharp
public sealed class ActiveProductsSpecification : Specification<Product>
{
    public ActiveProductsSpecification(int skip, int take)
        : base(product => product.IsActive)
    {
        ApplyPaging(skip, take); // TCJ2000
    }
}
```

Secondary ordering alone is not a replacement for a primary order:

```csharp
public sealed class ProductsSpecification : Specification<Product>
{
    public ProductsSpecification(int skip, int take)
    {
        ApplyThenBy(product => product.Id);
        ApplyPaging(skip, take); // TCJ2000
    }
}
```

### Corrected code

```csharp
public sealed class ActiveProductsSpecification : Specification<Product>
{
    public ActiveProductsSpecification(int skip, int take)
        : base(product => product.IsActive)
    {
        ApplyOrderBy(product => product.Name);
        ApplyThenBy(product => product.Id);
        ApplyPaging(skip, take);
    }
}
```

The primary order establishes the query ordering, while the secondary `Id` order provides a deterministic tie-breaker for equal names.

## Suppression

Suppress TCJ2000 only when deterministic ordering is guaranteed outside the construction path in a way the analyzer intentionally cannot prove, and that guarantee is stable for every consumer of the specification.

Prefer the narrowest standard suppression mechanism, such as a scoped `.editorconfig`, local pragma, or `SuppressMessage`. Suppression retains the risk of unstable offset pages if the external ordering guarantee changes or is not applied.

## Known limitations

TCJ2000 deliberately prefers false negatives over noisy false positives.

The analyzer handles simple constructor bodies and direct, source-defined, synchronous, non-virtual initialization helpers with linear execution. It may follow additional linear helper calls to prove that ordering exists and avoid a false positive, but paging nested beyond a directly invoked constructor helper is intentionally not diagnosed. It also declines to diagnose when proving the construction path would require reasoning through conditional/loop/exception control flow, constructor chaining, virtual or unresolved helper dispatch, custom intermediate `Specification<TEntity>` base constructors, cross-file/partial helper paths that are outside the current semantic model, multiple or unavailable source declarations, or other ambiguous current-instance mutations.

When a paging helper is shared by multiple constructors, the analyzer reports only when every relevant analyzed path is provably unordered. If an explicit constructor on the containing specification cannot be analyzed safely, or if an analyzed constructor that directly invokes the paging helper also establishes primary ordering, TCJ2000 does not report that helper invocation.

The rule does not infer ordering from arbitrary wrappers, delegates, reflection, dynamically bound calls, or methods whose names merely resemble `ApplyOrderBy` or `ApplyOrderByDescending`.

## Compatibility notes

TCJ2000 is a default `Warning` in the `TCJ.Specifications` category. It adds compile-time guidance only and does not change `Specification<TEntity>`, query execution, ordering, paging, or Entity Framework Core runtime behavior.

The rule intentionally has no code fix because choosing or changing an ordering key is not a semantics-preserving transformation that TCJ can derive automatically.
