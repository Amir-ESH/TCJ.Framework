# TCJ1000: Repository implementation owns the persistence commit boundary

| Property | Value |
| --- | --- |
| ID | `TCJ1000` |
| Category | `TCJ.Persistence` |
| Default severity | `Warning` |
| Code fix | Unavailable |
| Introduced in | Unshipped |

## Cause

A concrete type that implements the TCJ `IRepository` marker calls a persistence commit API from repository implementation code.

TCJ repositories stage query and state-change operations. Transaction and persistence boundaries are intentionally owned separately by `IUnitOfWork` and by the application/use-case that coordinates the operation. Committing inside a repository can break composition across repositories, explicit transaction control, transactional outbox consistency, and application-level unit-of-work boundaries.

TCJ1000 reports repository-owned calls to:

- Entity Framework Core `DbContext.SaveChanges`;
- Entity Framework Core `DbContext.SaveChangesAsync`; and
- TCJ `IUnitOfWork.SaveChangesAsync`.

## Rule description

TCJ1000 analyzes invocation symbols only inside non-abstract classes that implement the TCJ `IRepository` marker. The marker can be implemented directly, inherited through a base class, or inherited through generic/custom repository contracts.

The analyzer resolves TCJ repository and unit-of-work contracts by metadata identity. It also resolves `Microsoft.EntityFrameworkCore.DbContext` by metadata identity without adding an Entity Framework Core runtime dependency to the analyzer assembly.

For Entity Framework Core commits, the invocation must resolve to an actual `DbContext.SaveChanges`/`SaveChangesAsync` member or an override of that member. For TCJ unit-of-work commits, the invocation must resolve to `IUnitOfWork.SaveChangesAsync` or to the concrete implementation selected for that interface member. Methods that merely have the same name are not matched.

Application services, unit-of-work implementations, interceptors, seeding infrastructure, and any other non-repository types are outside this rule even when they legitimately commit changes.

## How to fix

Remove the persistence commit from the repository and let the repository only stage the requested changes. Commit from the application/use-case boundary after all participating repository operations have completed.

For example, inject `IUnitOfWork` into the application service or use-case coordinator and call `SaveChangesAsync` there after repository operations have been composed.

No automatic code fix is offered. Moving a persistence boundary is a semantic refactor: TCJ cannot safely determine the correct application/use-case owner, transaction scope, ordering, or outbox coordination from local syntax alone.

## Examples

### Code with diagnostic

```csharp
using Microsoft.EntityFrameworkCore;
using TCJ.EntityFrameworkCore.Repositories;

public sealed class OrderRepository : IRepository
{
    private readonly DbContext _dbContext;

    public OrderRepository(DbContext dbContext)
    {
        _dbContext = dbContext;
    }

    public Task CommitAsync(CancellationToken cancellationToken) =>
        _dbContext.SaveChangesAsync(cancellationToken); // TCJ1000
}
```

### Corrected code

```csharp
using TCJ.EntityFrameworkCore.Repositories;
using TCJ.EntityFrameworkCore.UnitOfWork;

public sealed class OrderApplicationService
{
    private readonly OrderRepository _repository;
    private readonly IUnitOfWork _unitOfWork;

    public OrderApplicationService(
        OrderRepository repository,
        IUnitOfWork unitOfWork)
    {
        _repository = repository;
        _unitOfWork = unitOfWork;
    }

    public async Task ExecuteAsync(CancellationToken cancellationToken)
    {
        await _repository.StageChangesAsync(cancellationToken);
        await _unitOfWork.SaveChangesAsync(cancellationToken);
    }
}
```

## Suppression

Suppress TCJ1000 only when a type intentionally implements the TCJ repository marker but is not participating in TCJ's repository/unit-of-work boundary contract and the ownership difference has been reviewed explicitly.

Prefer the narrowest standard suppression mechanism, such as a scoped `.editorconfig`, local pragma, or `SuppressMessage`. Suppression keeps the repository-owned commit behavior and therefore retains the transaction-composition and consistency risks described above.

## Known limitations

TCJ1000 deliberately matches only the commit APIs named in the rule contract. It does not infer persistence side effects hidden behind arbitrary wrappers, delegates, reflection, dynamically bound calls, or unrelated abstractions.

An extension method whose name resembles `SaveChanges` or `SaveChangesAsync` is not assumed to commit merely because of its name. Likewise, an unrelated `SaveChangesAsync` method is not reported.

The rule analyzes only concrete repository implementation classes. Commit code that exists solely in an abstract non-concrete type is not reported until it appears in analyzed concrete repository implementation code.

## Compatibility notes

TCJ1000 is a default `Warning` in the `TCJ.Persistence` category. It adds compile-time guidance only and does not change repository, Entity Framework Core, unit-of-work, transaction, or outbox runtime behavior.

The rule intentionally has no code fix because relocating a persistence boundary cannot be proven semantics-preserving automatically.
