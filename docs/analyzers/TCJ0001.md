# TCJ0001: Dependency type has conflicting TCJ lifetime markers

| Property | Value |
| --- | --- |
| ID | `TCJ0001` |
| Category | `TCJ.DependencyInjection` |
| Default severity | `Error` |
| Code fix | Mandatory |
| Introduced in | Unshipped |

## Cause

An effectively public concrete class that participates in TCJ convention-based dependency registration implements more than one of the six TCJ lifetime marker interfaces:

- `ITransientDependency`
- `IScopedDependency`
- `ISingletonDependency`
- `ISelfTransientDependency`
- `ISelfScopedDependency`
- `ISelfSingletonDependency`

The conflict includes markers inherited through base classes or custom interfaces. The runtime convention scanner rejects the same multi-marker state deterministically, so the analyzer reports it at compile time instead of allowing application startup or registration to fail later.

## Rule description

TCJ0001 inspects effectively public, non-abstract classes and resolves lifetime markers by their metadata names. Marker inheritance is included, so a class does not need to list a TCJ marker directly for that marker to participate in conflict detection.

The reported marker list follows TCJ's stable runtime lifetime-definition order and therefore does not depend on the order in which interfaces are written in source.

The analyzer preserves the runtime scanner boundary for compiler-generated types and `IDomainEventHandler<T>` implementations, which the convention dependency-registration path does not validate as marked dependencies.

## How to fix

Choose the single TCJ lifetime and registration mode that the dependency is intended to use, then remove the other conflicting TCJ lifetime markers.

When the conflicting markers are directly removable from the reported type declaration, the code fix offers one explicit action per safe marker choice, such as `Keep IScopedDependency`. The selected action removes only the other conflicting TCJ marker interfaces. Base classes, service contracts, and other non-TCJ interfaces are preserved.

If a conflicting marker is inherited through a custom interface or base class, TCJ does not remove that non-TCJ declaration automatically. In those cases only locally safe choices are offered; otherwise the conflict must be resolved manually at its source.

## Examples

### Code with diagnostic

```csharp
using TCJ.DependencyInjection.Lifetimes;

public interface IClockService;

public sealed class ClockService :
    IClockService,
    ITransientDependency,
    ISingletonDependency;
```

`ClockService` produces TCJ0001 because it declares two incompatible TCJ lifetime markers.

### Corrected code

```csharp
using TCJ.DependencyInjection.Lifetimes;

public interface IClockService;

public sealed class ClockService :
    IClockService,
    ISingletonDependency;
```

The service contract remains intact and the dependency now has exactly one TCJ lifetime marker.

## Suppression

Suppression is appropriate only when the containing code is intentionally excluded from TCJ convention scanning and the team accepts that enabling scanning for the assembly later could surface the runtime validation failure. Prefer the narrowest standard suppression mechanism, such as a scoped `.editorconfig` entry or a local pragma.

Do not suppress TCJ0001 merely to keep a type with ambiguous TCJ registration semantics. Resolve the lifetime conflict instead.

## Known limitations

The analyzer does not infer which lifetime is correct. That is application semantics and must remain an explicit developer choice.

A code fix is not offered when applying the selected choice would require removing or editing a non-TCJ interface, changing a base class, or modifying an inherited marker declaration elsewhere. This prevents a local fix from changing unrelated types that may share the inherited contract.

For partial types, the diagnostic still considers the complete type symbol. A local code fix is offered only when all conflicting markers that must be removed for the selected choice are directly declared in the reported partial declaration.

## Compatibility notes

TCJ0001 is a default `Error` because it moves an existing deterministic runtime registration failure to compile time when the analyzer is enabled. It does not change the runtime convention scanner or any public runtime API.

Both service-interface registration markers and self-registration markers participate in the same conflict check. Code fixes remove only conflicting TCJ marker interfaces that can be changed safely and locally.
