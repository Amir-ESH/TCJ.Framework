# TCJ0002: Interface lifetime marker requires a service contract

| Property | Value |
| --- | --- |
| ID | `TCJ0002` |
| Category | `TCJ.DependencyInjection` |
| Default severity | `Error` |
| Code fix | Mandatory when the marker is declared directly on the reported type |
| Introduced in | Unshipped |

## Cause

An effectively public concrete class uses `ITransientDependency`, `IScopedDependency`, or `ISingletonDependency` but exposes no interface that TCJ's convention scanner can register as a service contract.

The runtime scanner rejects this state during convention registration. TCJ0002 moves that deterministic failure to compile time when the analyzer is enabled.

## Rule description

TCJ0002 follows the runtime convention scanner's registration order and service-interface rules.

The rule applies only after a type resolves to exactly one TCJ lifetime marker. Types with conflicting lifetime markers are handled by TCJ0001 instead, and types that already use `ISelfTransientDependency`, `ISelfScopedDependency`, or `ISelfSingletonDependency` are valid without a service interface.

A service interface is eligible unless the runtime scanner excludes it. The following interfaces are not treated as service contracts:

- `IDependency` and interfaces that derive from it, including all TCJ lifetime markers.
- `IDisposable`.
- `IAsyncDisposable`.
- `IDomainEventHandler<TEvent>`.

Domain-event-handler implementations are excluded from TCJ0002 entirely because TCJ registers them through the dedicated domain-event registration path.

Generic service interfaces are eligible in the same way as the runtime scanner. For example, `Repository<T> : IRepository<T>, IScopedDependency` is valid because `IRepository<T>` is a service contract. For open generic implementation types, the runtime scanner later normalizes the generic service type during registration; that normalization does not change whether a service interface exists.

### Why interface and self-registration markers are separate

TCJ intentionally keeps interface-registration and self-registration markers separate because they express different service-resolution contracts, not merely different syntax.

`ITransientDependency`, `IScopedDependency`, and `ISingletonDependency` register the implementation through its eligible service interfaces. This keeps consumers coupled to service contracts and allows one implementation to expose one or more explicit abstractions.

`ISelfTransientDependency`, `ISelfScopedDependency`, and `ISelfSingletonDependency` register the concrete implementation type as itself. They are appropriate when the concrete type is intentionally the resolution contract and no service interface should be invented merely to satisfy convention scanning.

The code fix therefore preserves the original lifetime and changes only the registration mode.

## How to fix

Choose one of the following approaches:

1. Implement an eligible service interface when the type is intended to be resolved through a service contract.
2. Use the corresponding self-registration marker when the concrete type itself is intentionally the resolution contract.

When the lifetime marker is declared directly on the reported type, the code fix performs the second option automatically:

- `ITransientDependency` becomes `ISelfTransientDependency`.
- `IScopedDependency` becomes `ISelfScopedDependency`.
- `ISingletonDependency` becomes `ISelfSingletonDependency`.

The fix changes only the TCJ lifetime marker. Existing base classes, unrelated interfaces, modifiers, members, and the selected lifetime are preserved.

## Examples

### Code with diagnostic

```csharp
using System;
using TCJ.DependencyInjection.Lifetimes;

public sealed class Clock : IDisposable, IScopedDependency
{
    public void Dispose() { }
}
```

`IDisposable` is intentionally excluded from convention service contracts, so `Clock` produces TCJ0002.

### Corrected with a self-registration marker

```csharp
using System;
using TCJ.DependencyInjection.Lifetimes;

public sealed class Clock : IDisposable, ISelfScopedDependency
{
    public void Dispose() { }
}
```

The type remains scoped, but TCJ now registers `Clock` as itself.

### Corrected with a service contract

```csharp
using TCJ.DependencyInjection.Lifetimes;

public interface IClock;

public sealed class Clock : IClock, IScopedDependency;
```

No diagnostic is reported because `IClock` is an eligible service interface.

## Suppression

Suppress TCJ0002 only when the containing code is intentionally outside TCJ convention scanning and the team accepts that enabling scanning for that assembly later would still cause the runtime registration failure.

Prefer the narrowest standard suppression mechanism. Do not suppress the diagnostic merely to keep an interface-registration marker on a type that has no service contract.

## Known limitations

When the interface-registration lifetime marker is inherited through a custom interface or base class, TCJ0002 still reports the runtime-invalid type, but no local code fix is offered. Replacing that inherited marker would require editing or removing another type or interface, which could affect unrelated consumers and is not a safe automatic change.

For partial types, a code fix is offered only when the reported declaration directly contains the lifetime marker that can be replaced safely.

TCJ0002 mirrors the runtime scanner's exact disposal-interface exclusions. A custom interface that derives from `IDisposable` is still a distinct service interface and is therefore eligible under the current runtime rules.

## Compatibility notes

TCJ0002 does not modify runtime registration behavior or any runtime public API. It reports a source configuration that the current convention scanner already rejects deterministically.

The code fix preserves transient, scoped, or singleton lifetime exactly while switching from interface registration to self-registration. No service interface is invented and no unrelated interface is removed.
