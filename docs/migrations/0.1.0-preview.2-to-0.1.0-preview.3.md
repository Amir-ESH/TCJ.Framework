# Migrate from 0.1.0-preview.2 to 0.1.0-preview.3

This guide covers the supported upgrade from **0.1.0-preview.2** to the published **0.1.0-preview.3** release for all five TCJ Framework packages.

## Upgrade the package set

Upgrade all TCJ packages together when they are used in the same application. `0.1.0-preview.3` is published on NuGet.org; pin the same version across the package set:

```bash
dotnet add package TCJ.Core --version 0.1.0-preview.3
dotnet add package TCJ.DependencyInjection --version 0.1.0-preview.3
dotnet add package TCJ.EntityFrameworkCore --version 0.1.0-preview.3
dotnet add package TCJ.EntityFrameworkCore.SqlServer --version 0.1.0-preview.3
dotnet add package TCJ.AspNetCore --version 0.1.0-preview.3
```

## Source compatibility

**No source changes are required for the validated 0.1.0-preview.2 to 0.1.0-preview.3 upgrade path.** The version-specific breaking-change manifest is empty. The six clean-room upgrade consumers must restore, build, and run from the same source tree against both versions before release readiness can be approved.

## Changed dependencies

No production package dependency change was introduced by `0.1.0-preview.3`. The package graph remains the same five-package architecture and package validation continues to compare the candidate against the immutable `0.1.0-preview.2` baseline.

The release infrastructure now separates local candidate restores from published-package restores. `smoke/NuGet.Config` remains the local candidate feed used by packaged Native AOT validation, while `smoke/NuGet.Published.Config` is NuGet.org-only and is used by published-package smoke and dependency-audit restores.

## Changed defaults

No runtime default is changed for TCJ consumers. Retry, timeout, circuit-breaker, health-check, outbox, serialization, repository, Unit of Work, and middleware defaults remain unchanged by this release-infrastructure work.

## Configuration

No application configuration key or options binding change is required. Applications can keep their existing TCJ configuration and update the package set directly to `0.1.0-preview.3`.

## Dependency injection

No dependency injection registration change is required. Existing explicit or convention-based `TCJ.DependencyInjection` registrations continue to work without source changes.

## Middleware

No ASP.NET Core middleware ordering or registration change is required. Existing `AddTcjAspNetCore()` and `UseTcjAspNetCore()` usage remains valid.

## Entity Framework Core

No Entity Framework Core model, repository, Unit of Work, auditing, soft-delete, seeding, or interceptor behavior changes are introduced by this development increment.

## SQL Server

No SQL Server provider registration, rowversion, resilience, migration-readiness, or transaction behavior changes are introduced by this development increment.

## Transactional outbox

The **transactional outbox is opt-in**. Existing applications that do not call `AddTcjOutbox` remain outbox-disabled and do not gain an outbox table or processor merely by upgrading packages.

Consumers that enable the outbox continue to own the `TCJ_OutboxMessages` schema through a **consumer-controlled migration**. TCJ does not create or migrate that table automatically. Persisted **event type names are compatibility contracts**; keep stable event names when upgrading or provide an explicit application migration strategy for previously persisted messages.

No outbox schema, event-name, or processing-default change was introduced by `0.1.0-preview.3`.

## Behavior

The intended consumer-visible runtime behavior is unchanged. The current development work fixes release packaging and published-package verification infrastructure:

- each NuGet package now receives its own package-specific Markdown README from `docs/nuget/` instead of the GitHub repository README;
- published-package smoke restores explicitly use a NuGet.org-only configuration and no longer depend on the local `artifacts/packages` feed existing;
- release validation verifies the package README source and Markdown policy before publication.

These changes affect package presentation and release verification, not the public runtime API or application behavior.

## Rollback

If a deployment-specific problem is discovered after upgrading to `0.1.0-preview.3`, roll back every TCJ package in the application to `0.1.0-preview.2` together and perform a clean restore/build. No application data rollback is required by the changes documented in this guide because they do not introduce a runtime data or schema migration.

## Known limitations

This guide covers only the explicitly validated `0.1.0-preview.2` to `0.1.0-preview.3` preview-to-preview path. It does not imply compatibility with arbitrary future previews or untested platform/provider combinations. EF Core and SQL Server Native AOT support remains experimental under the repository's existing policy, while the documented Full support tier remains limited to the verified package paths.
