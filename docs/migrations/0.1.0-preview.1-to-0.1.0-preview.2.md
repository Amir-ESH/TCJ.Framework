# Migrate from 0.1.0-preview.1 to 0.1.0-preview.2

This guide covers the supported upgrade from **0.1.0-preview.1** to **0.1.0-preview.2** for all five TCJ Framework packages.

## Package update commands

Update every TCJ package used by the application to the same target version. For example:

```bash
dotnet add package TCJ.Core --version 0.1.0-preview.2
dotnet add package TCJ.DependencyInjection --version 0.1.0-preview.2
dotnet add package TCJ.EntityFrameworkCore --version 0.1.0-preview.2
dotnet add package TCJ.EntityFrameworkCore.SqlServer --version 0.1.0-preview.2
dotnet add package TCJ.AspNetCore --version 0.1.0-preview.2
```

Only run commands for packages your application references, but keep all TCJ package versions aligned.

## Required code modifications

**No source changes are required for the validated 0.1.0-preview.1 to 0.1.0-preview.2 upgrade path.** The breaking-change manifest is empty. Clean-room consumers are required to compile and run on both versions from the same source tree.

Before:

```xml
<PackageReference Include="TCJ.Core" Version="0.1.0-preview.1" />
```

After:

```xml
<PackageReference Include="TCJ.Core" Version="0.1.0-preview.2" />
```

## Changed dependencies

No consumer action is currently required for dependency changes in this upgrade. The upgrade suite captures the complete baseline and target NuGet graphs and reports any additions, removals, upgrades, downgrades, or asset-selection changes. Dependency downgrades and missing runtime assets are blocking.

## Changed defaults

No consumer-facing default change requiring migration has been identified. Any future changed default affecting this version pair must be documented here and represented in the upgrade behavior fixtures before release.

## Renamed or removed APIs

No approved renamed or removed public API requires a consumer source change for this path. Public API compatibility validation remains a separate release gate.

## Configuration changes

No configuration file or options migration is required. Existing package configuration should remain valid after the version update.

## Dependency Injection changes

No Dependency Injection registration migration is required. Transient, scoped, singleton, self-registration, duplicate-registration, and framework-service resolution semantics are exercised before and after the upgrade.

## Middleware order changes

No ASP.NET Core middleware-order migration is required. Existing `AddTcjAspNetCore` and `UseTcjAspNetCore` setup is expected to continue working without reordering.

## Entity Framework Core changes

No Entity Framework Core source migration is required. The upgrade suite validates provider-independent registration, repository and Unit of Work resolution, model creation, auditing, soft delete, specifications, and reading persisted SQLite data written by the baseline package.

## SQL Server changes

No SQL Server registration or options migration is required. Provider selection, connection metadata, command timeout, dependency closure, and service resolution are validated without opening a permanent database connection. Container-backed SQL Server tests continue to validate real database behavior separately.

## Behavioral changes

No documented runtime behavior change is expected for the maintained scenarios. Baseline and target scenarios must emit equivalent normalized behavior. Any non-equivalent result without an approved breaking-change entry is an unexpected regression and blocks release.

## Rollback

If a deployment-specific issue requires rollback, restore every TCJ package to `0.1.0-preview.1` together and perform a clean restore/build:

```bash
dotnet add package TCJ.Core --version 0.1.0-preview.1
dotnet restore --force-evaluate
dotnet build -c Release
```

Repeat the package command for every TCJ package your application uses. Review application data changes made after deployment before rolling back database-dependent applications.

## Known limitations

This guide describes the explicitly tested `0.1.0-preview.1` to `0.1.0-preview.2` preview-to-preview path. It is not a general promise that every future preview is source- or behavior-compatible. SQL Server registration is exercised in the upgrade consumer without a live database; real SQL Server storage, migrations, transactions, concurrency, and provider behavior remain covered by the dedicated container integration tests. Platform-specific behavior outside the maintained scenarios is not implied by this guide.
