# Migrate from 0.1.0-preview.4 to 0.1.0-preview.5

This guide tracks the supported upgrade from the published **0.1.0-preview.4** release to the current **0.1.0-preview.5** development line. Preview.5 contains twelve runtime TCJ Framework packages: the five pre-messaging runtime packages, the opt-in `TCJ.Messaging` transport family, and the new opt-in `TCJ.Messaging.Sagas`, `TCJ.Messaging.Sagas.EntityFrameworkCore`, and `TCJ.Messaging.Sagas.EntityFrameworkCore.SqlServer` packages. The analyzer-only `TCJ.Generators` tooling package remains part of the aligned release set.

## Upgrade the package set

`0.1.0-preview.4` is the latest published preview. `0.1.0-preview.5` is under development and must not be treated as a published NuGet.org release until its release workflow completes.

During development, public consumers should remain on `0.1.0-preview.4`. When preview.5 is eventually released, keep all referenced TCJ runtime packages on the same version and keep `TCJ.Generators` aligned when Strong Types are used. `TCJ.Messaging` and the Saga package family are opt-in; existing applications do not acquire Saga persistence or SQL Server Saga behavior unless they reference and register those packages explicitly.

## Source compatibility

Preview.5 adds opt-in transactional Inbox, transport-neutral messaging, and durable Saga orchestration. **No source changes are required** for existing consumers that do not enable these features; Step 51 does not remove or rename existing public APIs.

## Changed dependencies

Existing runtime package dependency graphs remain unchanged. `TCJ.Messaging.Sagas` depends only on the neutral messaging/Core contracts; `TCJ.Messaging.Sagas.EntityFrameworkCore` adds provider-neutral EF Core persistence; and `TCJ.Messaging.Sagas.EntityFrameworkCore.SqlServer` is the SQL Server leaf. Existing packages do not gain Saga dependencies, and broker SDKs do not leak into the Saga package family.

## Changed defaults

No existing runtime default changes are introduced by the new package families. Messaging and Saga orchestration remain opt-in and use bounded defaults documented in `eng/messaging-contract.json` and `eng/sagas-contract.json`.

## Configuration

No configuration change is required for existing consumers. Inbox consumers must continue to configure a stable `ConsumerName`, message contracts, handlers, payload-retention policy, and bounded retry/lease settings. Messaging consumers configure `TcjMessagingOptions`, stable logical message names, schema versions, and a transport adapter explicitly.

Saga consumers additionally configure `TcjSagaOptions`, explicit Saga definitions, stable logical Saga/message contracts, deterministic correlation, and caller-provided `JsonTypeInfo<TState>` metadata.

## Dependency injection

Existing consumers require no DI changes. Inbox adoption remains explicit through `AddTcjInbox`/`AddTcjSqlServerInbox`, stable message registration, one handler registration per CLR message type, and optional `AddTcjInboxProcessor` for deferred processing.

Messaging adoption is separately explicit through `AddTcjMessaging`, stable message-contract registrations, and an adapter registration. `AddTcjMessagingOutboxBridge` is also opt-in and is required only when committed Outbox deliveries should publish through the transport-neutral messaging abstraction.

Saga adoption is explicit through the provider registration (for SQL Server, `AddTcjSqlServerSagas<TDbContext>()`) and `AddTcjSaga<TDbContext, TSaga, TState>(...)`. External Saga messages must use the same `TDbContext` configured for transactional Inbox and Outbox processing.

## Middleware

No ASP.NET Core middleware ordering or registration changes are required for existing consumers. `TCJ.Messaging` does not add or reorder ASP.NET Core middleware.

## Entity Framework Core

Consumers that enable Inbox must map `modelBuilder.AddTcjInbox()` and create a consumer-owned migration for `TCJ_InboxMessages`. Existing consumers that leave Inbox disabled do not acquire this schema requirement.

Messaging itself has no direct EF Core dependency. Outbox-enabled consumers adopting preview.5 should review the additional nullable Outbox trace metadata described below and create a consumer-controlled migration when they use the updated Outbox mapping.

Saga persistence is introduced only by `TCJ.Messaging.Sagas.EntityFrameworkCore`. Consumers that enable it must add the provider Saga model extension and create/review their own migration for `TCJ_SagaInstances`, `TCJ_SagaCorrelations`, and `TCJ_SagaTimers`; TCJ never applies these migrations automatically.

## SQL Server

SQL Server Inbox consumers require the `TCJ_InboxMessages` table, the unique `(ConsumerName, MessageId)` index, and the processing/lease indexes documented in `eng/inbox-contract.json`. TCJ does not apply migrations automatically.

SQL Server Outbox consumers that adopt the preview.5 mapping should add the nullable trace metadata columns described below. These additions do not change the Outbox delivery guarantee or locking model.

SQL Server Saga consumers use `rowversion` optimistic concurrency, a filtered unique active-correlation index, and lease-based atomic timer claiming. These database objects belong in the consumer-owned migration generated from `AddTcjSqlServerSagas()`.

## Transactional outbox

The transactional outbox is opt-in. Existing applications that do not call `AddTcjOutbox` remain outbox-disabled. Consumers that enable it continue to own the `TCJ_OutboxMessages` schema through a consumer-controlled migration. Persisted event type names are compatibility contracts; keep stable event names when upgrading or provide an explicit application migration strategy for previously persisted messages.

Preview.5 keeps Outbox processing defaults and event-name semantics unchanged. The Outbox mapping includes nullable `CorrelationId` and `CausationId` metadata and now also persists nullable W3C trace metadata so an Outbox delivery can preserve trace lineage after the originating request `Activity` has ended:

```text
TraceParent nvarchar(55) NULL
TraceState  nvarchar(512) NULL
```

Existing Outbox-enabled consumers adopting the new mapping should generate and review a consumer-controlled migration that adds the nullable columns required by their current preview.5 model. The transactional outbox is opt-in, `AddTcjOutbox` remains explicit, and event type names are compatibility contracts.

## Transactional Inbox

Transactional Inbox is opt-in. Stable incoming message IDs and stable consumer names are operational compatibility contracts; changing a consumer name causes previously processed messages to enter a new idempotency boundary. Message-type names plus schema versions are wire compatibility contracts and should not be renamed for already-delivered or retained messages without an explicit migration strategy.

The Inbox guarantees effectively-once **committed database side effects** within one configured consumer boundary when Inbox state, business changes, and Outbox rows share the same transaction. Broker delivery remains at-least-once and TCJ does not claim global exactly-once delivery. Replay is explicit and preserves the original message identity.

## New package

`TCJ.Messaging`, `TCJ.Messaging.RabbitMQ`, `TCJ.Messaging.AzureServiceBus`, and `TCJ.Messaging.Kafka` are new opt-in runtime packages in `0.1.0-preview.5`. Existing consumers do not need to reference them unless they adopt transport-neutral messaging or one of the broker adapters.

`TCJ.Messaging.Sagas`, `TCJ.Messaging.Sagas.EntityFrameworkCore`, and `TCJ.Messaging.Sagas.EntityFrameworkCore.SqlServer` are also new target-only packages in preview.5. They provide transport-neutral Saga contracts, provider-neutral EF Core persistence, and SQL Server-specific concurrency/timer behavior respectively. Existing consumers do not acquire them transitively.

`TCJ.Messaging.AzureServiceBus` is explicitly registered and does not introduce Azure Service Bus SDK dependencies into neutral packages. Existing applications adopting the adapter must review queue/topic/subscription names as durable infrastructure contracts. Changing an entity name is an infrastructure migration, not a transparent package upgrade. Changing a non-session entity to require sessions (or the reverse) also requires coordinated infrastructure and deployment migration; do not flip the adapter setting independently of the broker entity.

Azure Service Bus duplicate detection remains broker-window-scoped and does not replace TCJ Inbox idempotency. Session ordering is scoped to one Service Bus session; preview.5 does not claim global ordering or global exactly-once delivery.

`TCJ.Messaging.Kafka` is also explicitly registered and keeps `Confluent.Kafka` isolated to the adapter package. Kafka topic names, partition counts, key selection, and consumer-group IDs are durable operational contracts. Changing a topic or group creates a new consumption boundary; changing partition counts can change future key-to-partition placement and therefore ordering behavior. Applications must migrate those values deliberately rather than treating them as transparent package configuration changes.

Kafka producer idempotence and broker-local retry do not replace TCJ Outbox or Inbox. Publication remains at-least-once logically, consumption remains at-least-once at the broker boundary, and application ordering is guaranteed only sequentially within a partition.

Logical `MessageType`, positive `MessageVersion`, stable message IDs, standard header names, publish outcomes, settlement outcomes, failure categories, and adapter capability names are wire compatibility contracts. Breaking payload changes require a new schema version or an explicit upcaster chain.

The built-in in-memory transport is non-durable and intended for tests and local development. Production broker adapters are separate concerns and must preserve the transport-neutral contract and conformance requirements.

## Durable Saga migration guidance

Persisted `SagaType`, definition versions, state-schema versions, transition/state names, timer names, and correlation semantics are compatibility contracts for active workflows. Do not rename or reinterpret them for in-flight Sagas without an explicit migration plan. Supported older state schemas should be migrated through registered `ISagaStateMigrator` steps; an unsupported active definition/schema version fails safely rather than being deserialized as a different contract. Saga ID and correlation identity remain stable across migration.

Compensation is a new durable business action, not rollback of a remote operation. Saga timers are Saga-owned deadlines, not a general-purpose scheduler. TCJ does not claim distributed ACID transactions, global exactly-once delivery, automatic remote rollback, or event-sourcing replay/reconstruction.

## Strongly Typed IDs and Value Objects

`TCJ.Generators` is part of the published package set beginning with `0.1.0-preview.4`. Keep direct generator references private and version-aligned with `TCJ.Core`. No generated API, scalar JSON, persistence-shape, or generator packaging change is currently recorded for preview.5.

## Behavior

Existing package behavior remains unchanged unless the opt-in messaging, Saga, Inbox, or Outbox features are explicitly enabled. Adding the Saga package family to the release set does not change runtime behavior for applications that do not reference and register it.

Broker delivery remains at-least-once. Inbox can provide effectively-once committed database side effects within its configured consumer boundary. TCJ does **not** claim global exactly-once delivery. Transport acknowledgement occurs only after the Inbox pipeline returns its committed outcome, and an Outbox record is marked processed only after the transport-facing publish path reports success.

## Rollback

Until preview.5 is published, public consumers should remain on `0.1.0-preview.4`. When rolling back an Inbox-enabled preview.5 deployment, stop Inbox processors first and preserve `TCJ_InboxMessages` until all old/new instances that may rely on its idempotency history are retired. Do not drop Inbox history during a mixed-version rollback.

When rolling back Messaging, stop consumers and publishers that depend on the new package before deploying preview.4 binaries. Nullable Outbox `CorrelationId`, `CausationId`, `TraceParent`, and `TraceState` columns may remain in place because preview.4 does not depend on them.

When rolling back a Saga-enabled preview.5 deployment, stop Saga message consumers and timer processors first. Preserve Saga, Inbox, and Outbox tables while any preview.5 instance or retained in-flight workflow may depend on them. Do not deploy preview.4 binaries that are expected to continue active preview.5 Saga instances; preview.4 has no Saga package/runtime contract.

## Known limitations

This document tracks only the explicitly validated `0.1.0-preview.4` to `0.1.0-preview.5` development upgrade path. It does not imply compatibility with arbitrary future previews or untested platform/provider combinations. The in-memory messaging adapter is non-durable and is not a production broker. EF Core and SQL Server Native AOT support remains experimental under the existing TCJ Native AOT policy.
