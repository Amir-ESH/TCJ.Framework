# Migrate from 0.1.0-preview.4 to 0.1.0-preview.5

This guide tracks the supported upgrade from the published **0.1.0-preview.4** release to the current **0.1.0-preview.5** development line for the five runtime TCJ Framework packages and the analyzer-only `TCJ.Generators` tooling package.

## Upgrade the package set

`0.1.0-preview.4` is the latest published preview. `0.1.0-preview.5` is under development and must not be treated as a published NuGet.org release until its release workflow completes.

During development, public consumers should remain on `0.1.0-preview.4`. When preview.5 is eventually released, keep all referenced TCJ runtime packages on the same version and keep `TCJ.Generators` aligned when Strong Types are used.

## Source compatibility

Preview.5 adds opt-in transactional Inbox APIs. **No source changes are required** for existing consumers that do not enable Inbox; no existing public API is removed or renamed by Step 45.

## Changed dependencies

No production package dependency changes are currently recorded for `0.1.0-preview.5`.

## Changed defaults

No runtime default changes are currently recorded for `0.1.0-preview.5`.

## Configuration

No configuration change is required for consumers that do not enable Inbox. Inbox consumers must configure a stable `ConsumerName`, message contracts, handlers, payload-retention policy, and bounded retry/lease settings.

## Dependency injection

Existing consumers require no DI changes. Inbox adoption is explicit through `AddTcjInbox`/`AddTcjSqlServerInbox`, stable message registration, one handler registration per CLR message type, and optional `AddTcjInboxProcessor` for deferred processing.

## Middleware

No ASP.NET Core middleware ordering or registration changes are currently recorded.

## Entity Framework Core

Consumers that enable Inbox must map `modelBuilder.AddTcjInbox()` and create a consumer-owned migration for `TCJ_InboxMessages`. Existing consumers that leave Inbox disabled do not acquire this schema requirement.

## SQL Server

SQL Server Inbox consumers require the `TCJ_InboxMessages` table, the unique `(ConsumerName, MessageId)` index, and the processing/lease indexes documented in `eng/inbox-contract.json`. TCJ does not apply migrations automatically.

## Transactional outbox

The transactional outbox is opt-in. Existing applications that do not call `AddTcjOutbox` remain outbox-disabled. Consumers that enable it continue to own the `TCJ_OutboxMessages` schema through a consumer-controlled migration. Persisted event type names are compatibility contracts; keep stable event names when upgrading or provide an explicit application migration strategy for previously persisted messages.

Preview.5 keeps Outbox processing defaults and event-name semantics unchanged, but the Outbox mapping adds nullable `CorrelationId` and `CausationId` metadata for Inbox-to-Outbox trace lineage. Existing Outbox-enabled consumers adopting the new mapping should add those nullable columns through a consumer-controlled migration. The transactional outbox is opt-in, `AddTcjOutbox` remains explicit, and persisted event type names are compatibility contracts.

## Transactional Inbox

Transactional Inbox is opt-in. Stable incoming message IDs and stable consumer names are operational compatibility contracts; changing a consumer name causes previously processed messages to enter a new idempotency boundary. Message-type names plus schema versions are wire compatibility contracts and should not be renamed for already-delivered or retained messages without an explicit migration strategy.

The Inbox guarantees effectively-once **committed database side effects** within one configured consumer boundary when Inbox state, business changes, and Outbox rows share the same transaction. Broker delivery remains at-least-once and TCJ does not claim global exactly-once delivery. Replay is explicit and preserves the original message identity.

## Strongly Typed IDs and Value Objects

`TCJ.Generators` is part of the published package set beginning with `0.1.0-preview.4`. Keep direct generator references private and version-aligned with `TCJ.Core`. No generated API, scalar JSON, persistence-shape, or generator packaging change is currently recorded for preview.5.

## Behavior

No consumer-visible behavior changes are currently recorded for `0.1.0-preview.5`.

## Rollback

Until preview.5 is published, public consumers should remain on `0.1.0-preview.4`. When rolling back an Inbox-enabled preview.5 deployment, stop Inbox processors first and preserve `TCJ_InboxMessages` until all old/new instances that may rely on its idempotency history are retired. Do not drop Inbox history during a mixed-version rollback. Nullable Outbox `CorrelationId`/`CausationId` columns may remain in place when rolling back because preview.4 does not depend on them.

## Known limitations

This document tracks only the explicitly validated `0.1.0-preview.4` to `0.1.0-preview.5` development upgrade path. It does not imply compatibility with arbitrary future previews or untested platform/provider combinations. EF Core and SQL Server Native AOT support remains experimental under the existing TCJ Native AOT policy.
